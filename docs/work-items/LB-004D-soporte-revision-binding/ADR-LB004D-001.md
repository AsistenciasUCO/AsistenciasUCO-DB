# ADR-LB004D-001 — Persistencia durable del vínculo soporte ↔ solicitud de revisión

```text
ESTADO: PROPUESTO — REVISIÓN DEL OWNER DB (John) PENDIENTE
LB004D_ARCHITECTURE: ONE_TABLE (decisión del solicitante, 2026-10-19)
LB004D_CONTRACT_APPROVED: NO (aprobación de John no registrada; no se inventa)
BASE: develop 7d9c050 (merge PR #37, P0-D)
BASELINE_CONTRACT: UNCHANGED (sha 45e48c5a…)
GOLDEN_PATH: FROZEN — esta propuesta no toca ningún archivo del manifest
```

Historial: la primera versión de este ADR proponía dos tablas (`ArchivoSoporte` +
`ArchivoSoporteTransicion`). El solicitante decidió **una sola tabla nueva**; esta revisión lo
refleja sin perder los análisis de seguridad (§6). La implementación D1 está publicada en una rama
y desplegada de forma aditiva en la base local de desarrollo, pero **no se declara aprobada**: el
owner DB debe revisar firmas, grants y reglas de negocio (preguntas abiertas Q5, Q6, Q9 en
[CONTRACT_PROPOSAL](CONTRACT_PROPOSAL.md#7-decisiones-del-owner-db)).

## 1. Contexto

- El backend (`alejovh12/AsistenciasUCO`, PR #27, `develop e6c4df6`) ya valida, analiza con ClamAV
  y almacena los soportes en MinIO bajo un `fileId` UUID generado por backend. La metadata
  temporal vive solo en el objeto MinIO (`owner-subject`, checksum, tamaños…).
- AS-IS DB verificado en `develop 7d9c050`:
  - `SolicitudRevisionAsistencia` no tiene ninguna columna de soporte.
  - `usp_radicar_solicitud_revision_asistencia` recibe `@soporteNombre`/`@soporteUrl` y **los
    descarta** (el `INSERT` no los usa).
  - `usp_resolver_solicitud_revision_asistencia` sí resuelve
    `SolicitudRevisionAsistencia → Asistencia → Sesion → Grupo.docente`.
  - No existe SP/vista de lectura de reclamos para el docente (`GET /docente/reclamos` responde
    `FeatureUnavailable` en backend).
- Sin vínculo durable SQL, el docente titular no puede descargar el soporte de forma autorizada
  (`DOCENTE_FILE_ACCESS: DENY_BY_DEFAULT`) y los objetos MinIO no pueden reconciliarse por estado
  durable (ya existe un huérfano técnico real del 2026-09-30 en el bucket local).
- Decisión del profesor (backend `PROFESSOR_DECISION.md`): bytes fuera de SQL; SQL Server es la
  autoridad de negocio y conserva la referencia lógica del objeto junto con la revisión.

## 2. Requisitos que la decisión debe cumplir

1. Identidad `fileId` UUID opaca, generada por backend; nunca filename, URL ni `objectKey`.
2. Propietario institucional = `idUsuario` resuelto del JWT (`@idUsuarioEjecutor`), nunca un campo
   del request.
3. Estados `DRAFT`, `ATTACHED`, `ORPHAN` (`REPLACED` reservado) con transiciones verificables y fechas UTC `DATETIME2(7)`.
4. Un archivo se asocia a lo sumo a una solicitud y nunca se reutiliza tras `ATTACHED`.
5. Asociación atómica con la radicación (rollback no deja reclamo con soporte a medias).
6. Lectura autorizada solo para el estudiante propietario y el docente titular del grupo de la
   sesión del reclamo; cualquier otro actor obtiene 0 filas (backend → 404).
7. Reconciliación de huérfanos por estado durable, sin plazos inventados.
8. Sin cambios incompatibles en firmas/resultsets existentes (*Expand & Contract*), sin tocar el
   Golden Path congelado, sin permisos directos sobre tablas para `rol_asistencias_runtime`.

## 3. Alternativas evaluadas

| Criterio | A — Tabla nueva de metadata SQL desde `DRAFT` | B — Columnas en `SolicitudRevisionAsistencia` + metadata MinIO para `DRAFT` | C — Solo fila de binding al `ATTACH`; `DRAFT` en MinIO |
|---|---|---|---|
| Cambia tabla existente | No (objeto nuevo) | **Sí** (expande `SolicitudRevisionAsistencia`, contrario al principio del baseline) | No |
| Trazabilidad SQL del `DRAFT` | Completa | Ninguna | Ninguna |
| Propietario verificable por SQL antes de adjuntar | Sí (`usuarioPropietario`) | No: depende de `owner-subject` de MinIO, que no es autoridad | No: ídem |
| Atomicidad attach + radicación | Sí (una transacción SQL) | Sí | Sí, pero sin comprobar en SQL la propiedad previa |
| Reconciliación de huérfanos | Por consulta SQL de estado/fecha (SP diferidos, Q6) | Requiere listar/consultar metadata MinIO a escala (capacidad no evidenciada) | Ídem B |
| Checksum autoritativo para la descarga | SQL | MinIO | SQL solo tras attach |
| Docente titular por SQL | Join directo `ArchivoSoporte → Solicitud → … → Grupo.docente` | Join directo | Join directo |
| Costo | 1 tabla, 1 SP v2, SP de registro y de lectura | Migración de tabla existente + misma lectura | 1 tabla + misma lectura, lógica de propiedad en MinIO |
| Riesgo de seguridad | Bajo | Alto (`soporteUrl` como dato de confianza) | Medio |

## 4. Decisión propuesta

**Alternativa A, simplificada a UNA tabla — metadata SQL durable desde `DRAFT`**, con:

- Una única tabla nueva `dbo.ArchivoSoporte` (una fila por `fileId`). No hay tabla de
  transiciones, de estados, de proveedores ni de configuración: el ciclo de vida queda en
  `estado` + tres fechas UTC (`DATETIME2(7)`) + dos correlaciones de la propia fila.
- Registro del `DRAFT` por SP público nuevo inmediatamente después del `put` en MinIO.
- Asociación dentro de un **nuevo** `usp_radicar_solicitud_revision_asistencia_v2`, atómica con la
  radicación; la v1 queda intacta y sin cambios de firma ni resultset.
- Lectura autorizada por SP que une tablas base (sin `SESSION_CONTEXT` ni `uv_auth_*`) y devuelve
  0 filas cuando no hay relación.
- Reconciliación (SP de consulta/marcado con fecha de corte provista por el llamador) **diferida**:
  la ventana operacional sigue `PRODUCT_DECISION_REQUIRED` (Q6). El estado `ORPHAN` existe y es
  inaccesible para lectura.
- La referencia lógica que SQL conserva es el `fileId`. Bucket y `objectKey` son derivación interna
  de Infrastructure backend (`soportes/<fileId>`) y **no** se persisten en SQL.

## 5. Consecuencias

- Positivas: SQL es la autoridad del binding y del checksum; autorización docente verificable;
  reconciliación sin depender de capacidades no evidenciadas de MinIO; v1 intacta.
- Negativas: una tabla nueva, nuevos permisos, nuevo manifest post-freeze, migración coordinada
  del backend de v1 a v2 y del frontend de `soporteUrl` a `soporteArchivoId`. Sin tabla de
  transiciones, el historial se limita a la última transición por fila (suficiente para el flujo
  actual; una auditoría completa sería una decisión posterior, no un requisito de LB-004D).
- Independencia del proveedor: SQL conserva solo `fileId`; migrar a Azure Blob o S3 es un nuevo
  adaptador de Infrastructure más migración operacional de objetos, sin tocar `fileId` ni relaciones.
- Neutras: la v1 sigue aceptando `@soporteNombre/@soporteUrl` y descartándolos (comportamiento
  AS-IS); su retiro requiere una decisión contractual posterior.
